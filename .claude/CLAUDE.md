# CLAUDE.md

이 저장소에서 작업할 때의 지침이다. Kent Beck의 TDD와 Tidy First를 따른다.

## 1. 시작하기

이 저장소는 claude-code-base 템플릿이다. 템플릿을 복사해서 새 프로젝트를 시작했다면 다른 작업 전에 `/rw:init`을 먼저 실행한다. `/rw:init`은 프로젝트 스택(영역, 백엔드 스택, 언어, 아키텍처 스타일, 영속성 도구, 프론트엔드 프레임워크)을 감지하거나 질문으로 확정한 뒤, 해당하지 않는 `.claude/rules/`와 `.claude/agents/` 파일을 삭제한다. 상세는 `init.md`에 있다.

상호 배타적인 rules 파일(Java/Kotlin, Layered/Hexagonal, Next.js/Vite/Vue 등)은 `paths`만으로는 배제되지 않아 이 정리가 필요하다. 이미 실행했거나 이 저장소가 템플릿 원본이면 건너뛴다.

## 2. 개발 방법론

- TDD(Red → Green → Refactor)로 개발한다. 테스트 이름은 동작을 설명한다(예: `shouldSumTwoPositiveNumbers`).
- 결함 수정은 API 수준 실패 테스트와 문제를 재현하는 최소 테스트를 먼저 작성하고 둘 다 통과시킨다.
- Tidy First: 구조적 변경(이름 변경·추출·이동)과 동작 변경을 같은 커밋에 섞지 않는다. 둘 다 필요하면 구조적 변경을 먼저 한다. 구조적 변경 전후로 테스트를 실행해 동작이 바뀌지 않았음을 확인한다.

## 3. 커밋 규율

- 테스트가 통과하고 컴파일러·린터 경고가 모두 해결됐으며 변경이 하나의 논리적 단위일 때만 커밋한다.
- 크고 드문 커밋보다 작고 잦은 커밋을 택한다.
- 커밋 메시지에 구조적 변경인지 동작 변경인지 명시한다.
- 작업 완료 후 자동으로 커밋하지 않는다. 변경 내용과 결과를 먼저 보고하고, 사용자가 요청한 경우에만 커밋한다.

## 4. 코드 작성 기준

- 요청된 범위를 넘는 기능, 단일 사용처용 추상화, 요청되지 않은 설정 가능성, 발생 불가능한 시나리오의 에러 처리를 추가하지 않는다.
- 클래스 참조 시 FQCN을 본문에 직접 쓰지 않고 import문으로 추출한다.
- 기존 코드를 편집할 때 인접 코드·주석·포맷팅을 함께 "개선"하지 않고 기존 스타일을 따른다. 변경된 모든 줄이 사용자 요청으로 추적되어야 한다.
- 기존부터 있던 죽은 코드는 발견하면 언급만 하고 요청 없이 삭제하지 않는다. 본인 변경이 사용처 없게 만든 import/변수/함수만 제거한다.
- 해석이 여러 가지로 갈려 결과물이 달라지는 지점은 임의로 고르지 않고 가정을 명시하거나 질문한다.
- 비-TDD 작업(설정, 스크립트, 문서)도 각 단계와 그 검증 방법을 짝지어 진행한다.
- 완료를 보고하기 전에 실제 결과물을 실제 사용 조건 그대로 실행해 확인한다. 컴파일 성공, 서브에이전트의 자기 보고, 실제와 다른 조건의 실행(예: 따로 실행될 명령을 한 번에 이어서 실행)은 증거가 아니다. 확인에 쓴 명령은 다시 돌릴 수 있게 결과 보고에 남긴다. 커맨드·에이전트 문서에 분기나 선택지를 추가·변경했으면, 예시 입력으로 각 경로의 다음 동작(같은 실행의 다음 단계와 다음 실행)을 따라가 결과 보고에 적는다.

## 5. .claude 문서 작성

`.claude/` 아래 `.md`(`rules/`, `commands/`, `agents/`, `CLAUDE.md`, `guides/`)를 만들거나 고치기 전에 `.claude/guides/STYLE_GUIDE.md`를 먼저 읽는다. `README.md`와 `.claude/statusline.md`는 제외한다. 문서 유형(Rule/Command/Agent/Meta)마다 frontmatter와 헤딩 규약이 다르므로 옆 파일을 모방하지 않는다.
