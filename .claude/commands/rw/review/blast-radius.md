# /rw:review:blast-radius — 변경 영향 범위 분석

변경이 diff 밖의 어디를 깨뜨릴 수 있는지 찾습니다. 호출부 나열은 grep으로 금방 얻을 수 있으므로 이 커맨드의 목적이 아닙니다. 목적은 grep이 보여주지 않는 파손을 찾고, 변경이 안전하다는 판단이 기대는 핵심 사실을 그럴듯한 서술이 아니라 **실제 코드 실행으로 증명**하는 것입니다.

`code-reviewer`가 diff 안의 코드 품질을 본다면, 이 커맨드는 diff 밖으로 번지는 영향을 봅니다. 작아 보이지만 믿기 어려운 변경을 머지하기 전에 실행합니다.

## 1단계: 대상 변경 결정

`$ARGUMENTS`로 분기합니다.

### 경로 A: PR 번호가 입력된 경우

`#123`, `123`에서 숫자만 추출해 `gh pr diff {번호}`로 변경분을 가져옵니다.

### 경로 B: 커밋 범위나 SHA가 입력된 경우

`git diff {범위}` 또는 `git show {SHA}`로 변경분을 가져옵니다.

### 경로 C: `$ARGUMENTS`가 비어 있는 경우

1. `git diff HEAD`로 커밋되지 않은 변경(스테이징 포함)을 가져옵니다.
2. 비어 있으면 기본 브랜치를 판정한 뒤 `git diff {기본 브랜치}...HEAD`로 현재 브랜치의 변경을 가져옵니다.

어느 경로든 변경분이 비어 있으면 그 사실을 알리고 **중단**하세요.

## 2단계: 변경 내용 파악

1. 추가·변경·삭제된 심볼(함수, 클래스, 필드, 설정 키, 스키마, 엔드포인트)을 목록으로 만듭니다.
2. 변경 후 **달라지는 동작**을 적습니다. diff가 직접 드러내지 않는 변화(기본값 변경, 실행 순서 변경, 예외 타입 변경, null 처리 변경 등)를 함께 적습니다.

## 3단계: 안전 근거 사실 식별

위험해 보이는 변경도 대개 사실 하나 때문에 안전합니다(예: "이 메서드는 이미 만료된 캐시 항목만 지우고 다른 일은 하지 않는다"). 그 사실 하나가 성립하면 위험 시나리오 대부분이 한 번에 배제됩니다.

1. 이 변경의 안전성이 기대는 사실을 1~2개 찾아 한 문장씩 적습니다.
2. 분석 시간은 가능성 낮은 위험을 길게 나열하는 데보다 이 사실을 찾고 검증하는 데 씁니다.

## 4단계: grep이 닿지 않는 곳 탐색

심볼 검색으로 찾히는 직접 호출부 너머를 봅니다. 해당하는 항목만 확인합니다.

- **직렬화 경계**: API 응답 JSON, 메시지 페이로드, 캐시에 저장된 값처럼 다른 서비스·클라이언트·이전 버전 코드가 읽는 포맷.
- **영속 데이터**: DB 컬럼, 인덱스, 기존 행의 값. 마이그레이션 없이 바뀐 매핑, 기존 데이터와 새 제약의 충돌.
- **설정과 분기**: feature flag, 프로필별 설정, 환경 변수 기본값.
- **라이브러리 내부**: 호출하는 라이브러리의 실제 소스와 이 저장소가 고정한 버전. 문서가 아니라 고정 버전의 소스를 근거로 삼습니다.
- **실행 시점**: 트랜잭션 경계, 비동기·이벤트 처리 순서, 프레임워크 생명주기(빈 초기화, 컴포넌트 마운트·언마운트).
- **간접 참조**: 리플렉션, 문자열로 된 이름, 다른 언어로 작성된 소비자, 두세 단계 떨어진 하위 호출.

## 5단계: 확신 단계 판정

3단계의 사실과 4단계에서 찾은 위험마다 아래 단계 중 어디까지 확인했는지 판정합니다. 비용이 감당되는 한 아래쪽 단계까지 끌어내립니다.

| 단계 | 근거 |
|---|---|
| 1 | 주장만 있음. 그 자체로는 근거가 아님 |
| 2 | `파일:라인` 또는 라이브러리 소스의 해당 위치를 가리킴 |
| 3 | 실패 경로를 단계별로 따라가 도달하지 않음을 보임 |
| 4 | 실제 코드를 호출하는 스크립트나 테스트를 실행함 |
| 5 | 실행 중인 애플리케이션에서 재현함 |

## 6단계: 핵심 사실을 실행으로 증명

1. 3단계의 사실을 4단계 이상으로 증명하는 스크립트나 테스트를 작성합니다. 대개 애플리케이션과 같은 라이브러리를 가져와 우려하는 함수를 직접 호출하는 작은 코드 하나면 됩니다. 사실이 거짓이면 크게 실패하도록 작성합니다.
2. 저장소의 테스트 체계가 필요 없으면 저장소 밖 임시 디렉토리에 작성합니다. 테스트 체계가 필요하면 저장소 테스트 디렉토리에 작성하고, 결과 보고에 그 파일 경로를 명시합니다.
3. 실행하고 실제 출력을 기록합니다.
4. 증명하지 못하면 그 사실을 **미증명**으로 표기하고, 어느 단계에서 멈췄는지 적습니다.

## 결과 보고

다음 순서로 보고합니다.

- **변경 내용**: 무엇이 바뀌는지. 2단계 2항의 드러나지 않는 변화를 포함합니다.
- **안전 근거 사실**: 사실 한 문장, 도달한 확신 단계, 증거(실행 명령과 출력). 증명하지 못했으면 미증명으로 표기합니다.
- **위험**: 항목마다 `파일:라인`, 어떻게 깨지는지, 발생 가능성(높음/중간/낮음), 영향, 확인 방법. 중요한 항목에는 증명 출력을 붙입니다.
- **확인 후 배제**: 확인했고 문제없다고 판단한 항목과 그 이유.
- 6단계에서 저장소 안에 증명용 파일을 만들었다면 그 경로와, 테스트로 남길 가치가 있는지에 대한 의견.

## 하지 말아야 할 것

- grep으로 얻은 호출부 목록을 분석 결과로 내지 않는다.
- 확신 단계 1(주장만 있음)인 사실을 "안전하다"는 결론의 근거로 쓰지 않는다. 증명하지 못했으면 미증명이라고 쓴다.
- 존재하지 않는 호출부나 API를 추정해 쓰지 않는다. 검색 결과가 없으면 "없음"도 하나의 결론으로 보고한다.
- 분석 대상 코드를 수정하지 않는다. 6단계의 증명용 파일만 작성한다.
- 자동 커밋하지 않는다.
