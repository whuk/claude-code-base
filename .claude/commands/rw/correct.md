# /rw:correct — 반복 실수를 구조로 막기

같은 실수를 반복해서 지적하고 있다면, 다음 에이전트가 그 실수를 할 수 없도록 저장소를 바꿉니다. 에이전트는 자신이 연 파일만 보고, 가장 가까운 예시를 따라 하고, 컴파일되는 가장 짧은 경로를 택한다고 가정합니다. 문서 조항은 읽히지 않으면 아무것도 실패하지 않으므로 마지막 수단으로 둡니다(`STYLE_GUIDE.md` 9번).

## 1단계: 실수 흔적 수집

`$ARGUMENTS`로 분기합니다. 어느 경로든 2단계를 거칩니다.

### 경로 A: 교정할 실수가 입력된 경우

입력된 실수를 기준 패턴으로 삼습니다. 이번 지적 자체를 발생 1회로 세고, 그 위치(`파일:라인` 또는 커밋 SHA)를 증거로 기록합니다. 이어서 경로 B의 출처에서 **같은 패턴의 과거 발생만** 찾습니다.

### 경로 B: `$ARGUMENTS`가 비어 있는 경우

아래 출처에서 에이전트가 저지른 실수의 흔적을 모두 모읍니다.

### 출처 — 두 경로 공통

- 최근 커밋 이력에서 revert 커밋과, 직전 커밋을 바로잡는 fix 커밋을 찾습니다. 본문과 `Co-Authored-By` 같은 trailer까지 보고 에이전트가 만든 커밋과 그것을 바로잡은 커밋을 가려냅니다.
  ```bash
  git log --format='%h %s%n%b' -100
  ```
- 머지된 PR의 리뷰 코멘트를 봅니다. `gh pr view --comments`에는 줄 단위 리뷰 코멘트가 나오지 않으므로 `gh api`로 함께 조회합니다. `gh` CLI를 쓸 수 없으면 이 출처를 건너뛰고 결과 보고에 그 사실을 남깁니다.
  ```bash
  gh pr list --state merged --limit 30
  gh pr view {번호} --comments
  gh api repos/{owner}/{repo}/pulls/{번호}/comments
  ```
- 우회 방법을 설명하는 코드 주석.

다음 두 가지는 **참고 출처**입니다. 이미 대응 중인 규칙을 확인하는 데만 쓰고, 2단계의 발생 횟수에는 세지 않습니다. 조항은 실수가 실제로 일어난 사례가 아니기 때문입니다.

- `.claude/rules/`, `.claude/agents/`, `CLAUDE.md`의 금지 패턴 조항.
- `.claude/guides/enforced-rules.md`가 있으면 그 대응표.

## 2단계: 실수 클래스 분류

1. 1단계에서 모은 흔적을 같은 원인의 실수끼리 클래스로 묶습니다. **실제로 두 번 이상 발생한 것만** 클래스로 인정합니다. 경로 A에서 과거 발생을 찾지 못해 이번 지적 1회뿐이면 클래스로 만들지 않고, 그 사실을 보고한 뒤 **중단**하세요. 같은 실수가 다시 지적되면 그때 이 커맨드를 다시 실행합니다.
2. 클래스마다 발생 건별 증거(커밋 SHA, PR 코멘트 링크, `파일:라인`)를 붙입니다. 6단계의 증명은 이 증거를 재현합니다.
3. 참고 출처의 대응표나 금지 패턴에 이미 있는 규칙인데 다시 발생한 클래스에는 **재발**을 표시합니다. 재발은 기존 강제 수단이 실제로는 막지 못한다는 뜻이므로 우선순위를 높입니다.
4. 클래스를 발생 빈도 순으로 정렬합니다. 클래스가 하나도 없으면 그 사실을 보고하고 **중단**하세요.

## 3단계: 강제 수준 선택

클래스마다 아래 순서에서 가장 높은 수준을 고릅니다. 상위 수준을 쓸 수 없으면 그 이유를 적습니다.

1. **아키텍처로 제거**: 상태마다 소유자를 하나로, 작업마다 지원 경로를 하나로 만듭니다. 내부 구현을 감춰 잘못된 import가 실패하게 합니다. 수작업으로 동기화하는 목록은 단일 원천으로 바꿉니다. 에이전트가 따라 할 수 있는 낡은 방식과 죽은 코드를 지웁니다.
2. **타입으로 강제**: 잘못된 상태를 코드로 쓸 수 없게 합니다.
3. **린터·아키텍처 테스트**: 잘못된 코드가 여전히 컴파일되면 린터 규칙이나 ArchUnit 같은 아키텍처 테스트를 추가합니다. 에러 메시지에 대신 쓸 파일·타입·함수를 적습니다. 이미 코드베이스에 흔한 패턴이면 변경으로 새로 추가되는 경우만 실패하게 합니다.
4. **테스트**: 동작을 검증하는 테스트를 추가하거나 고칩니다. 동작이 깨져도 통과하거나 내부만 바뀌어도 실패하는 테스트는 고치거나 지웁니다(`code-review.md` 10번).
5. **문서**: 판단이 필요해 위 수준으로 막을 수 없는 경우에만 rules나 agents에 조항을 씁니다. 실패 사례 예시를 함께 둡니다.

## 4단계: 사용자 확인

클래스별로 증거, 선택한 수준, 상위 수준을 쓰지 못한 이유, 바꿀 파일 목록을 보여주고 **적용 여부를 확인받습니다.** 사용자가 일부만 승인하면 승인된 클래스만 5단계로 넘깁니다. 모두 거절하면 결과 보고로 넘어갑니다.

## 5단계: 한 클래스 적용

승인된 클래스 중 빈도가 가장 높은 **한 클래스만** 적용합니다.

1. 강제 수단을 구현합니다. 구조적 변경과 동작 변경이 함께 필요하면 구조적 변경만 먼저 적용하고, 기존 테스트가 통과하는지 확인한 뒤 결과를 보고하고 **중단**하세요(`CLAUDE.md` 2번). 사용자가 커밋한 뒤 진행을 요청하면 동작 변경부터 이어서 진행합니다.
2. 현재 코드에서 검사가 통과하는지 확인합니다. 로컬에서 실행한 명령이 CI에서도 같은 명령으로 실행되는지 확인합니다.
3. 기존 코드 중 검사를 통과하지 못하지만 당장 고칠 수 없는 곳이 있으면, 그 위치 목록과 남길 사유를 보여주고 **사용자에게 확인받은 뒤** 해당 줄에 사유를 남긴 예외로 처리합니다. 이 위치는 4단계에서 승인받은 파일 목록 밖일 수 있기 때문입니다. 거절하면 그 위치를 고치는 방안과 함께 이 클래스를 중단할지 묻습니다.

## 6단계: 과거 실수에 실패함을 증명

2단계 2항의 증거 중 하나를 아래 경로 중 하나로 재현해 새 검사를 실행하고, 실패 출력을 기록합니다. 실패 메시지가 **새 검사의 규칙 이름이나 에러 메시지인지 대조**합니다. 컴파일 오류, 의존성 누락처럼 다른 원인으로 난 실패는 증명으로 인정하지 않습니다. 그 원인을 해결하거나 다른 경로로 다시 재현합니다.

### 경로 A: 실수가 있던 과거 커밋에서 재현

과거 커밋에는 5단계에서 만든 검사가 없으므로, 저장소 밖 worktree로 그 커밋을 체크아웃한 뒤 검사를 옮겨 실행합니다.

- `mktemp -d`가 출력한 경로를 기록해 `{worktree 경로}`에 그대로 씁니다. 셸 변수는 다음 명령 호출까지 유지되지 않습니다.
- 저장소 밖으로 이동한 `cd`도 다음 호출까지 유지되지 않으므로, worktree 안에서 실행할 명령은 매번 `cd {worktree 경로} &&`로 시작합니다.

1. worktree를 만듭니다.
   ```bash
   mktemp -d
   git worktree add --detach {worktree 경로} {실수 커밋}
   ```
2. 5단계에서 **새로 만든** 검사 파일은 디렉토리를 만든 뒤 같은 경로에 복사합니다. 과거 커밋에 그 디렉토리가 없을 수 있습니다.
   ```bash
   mkdir -p {worktree 경로}/{검사 파일 디렉토리}
   cp {검사 파일} {worktree 경로}/{검사 파일}
   ```
3. 5단계에서 **기존 파일을 수정**했으면(린터 설정, 빌드 파일의 플러그인 추가 등) 파일을 통째로 복사하지 않고 변경분만 적용합니다. 통째로 복사하면 과거 커밋의 다른 내용까지 덮어씁니다. 적용이 실패하면 경로 B로 재현합니다.
   ```bash
   git diff -- {수정 파일} | git -C {worktree 경로} apply
   ```
4. worktree에서 설치·빌드를 한 뒤 검사를 실행합니다. 새 worktree에는 설치된 의존성과 빌드 산출물이 없습니다.
   ```bash
   cd {worktree 경로} && {설치·빌드 명령}
   cd {worktree 경로} && {검사 명령}
   ```
5. 실패 출력을 기록한 뒤 worktree를 제거합니다.
   ```bash
   git worktree remove --force {worktree 경로}
   ```

### 경로 B: 현재 트리에서 임시 재현

5단계의 변경이 커밋되지 않은 채 남아 있으므로 작업 트리는 깨끗하지 않습니다. 판정 기준은 깨끗한 상태가 아니라 **재현 전과 같은 상태**입니다.

1. 재현 전 상태를 기록합니다. 이미 수정된 파일에 임시 패턴을 쓰면 `git status --porcelain`의 출력은 바뀌지 않으므로, 변경 내용의 해시도 함께 기록합니다.
   ```bash
   git status --porcelain
   git diff | shasum
   ```
2. 같은 실수 패턴을 현재 트리에 임시로 작성하고 검사를 실행해 실패 출력을 기록합니다.
3. 임시 작성분을 되돌린 뒤 1항의 두 명령을 다시 실행해, 두 출력이 모두 재현 전과 같은지 비교합니다.

## 7단계: 대응표 갱신과 클래스 단위 중단

`.claude/guides/enforced-rules.md`에 규칙과 그 규칙을 강제하는 수단의 대응표를 유지합니다. 파일이 없으면 `.claude/guides/STYLE_GUIDE.md`를 먼저 읽고 Meta 문서 규약(H1, 목적 진술, 번호 매긴 섹션)에 맞춰 만듭니다.

1. 5단계에서 적용한 클래스의 행을 추가합니다.

   ```markdown
   | 규칙 | 강제 수단 | 위치 | 과거 실수 증거 |
   |---|---|---|---|
   | Controller가 Repository를 직접 참조하지 않는다 | ArchUnit 테스트 | `ArchitectureTest.java:42` | `a1b2c3d` |
   ```

2. 재발한 규칙은 기존 행의 강제 수단을 새 수단으로 바꿉니다.
3. 구조로 막혀 더 이상 발생할 수 없게 된 문서 조항이 rules나 agents에 남아 있으면, 강제 수단을 가리키는 한 줄로 줄이자고 결과 보고에서 제안합니다. 승인 없이 지우지 않습니다.
4. 이 클래스의 결과를 보고하고 **중단**하세요. 이 커맨드는 커밋하지 않으므로, 다음 클래스를 이어서 적용하면 여러 클래스의 변경이 한 작업 트리에 섞입니다. 사용자가 커밋한 뒤 다음 클래스 진행을 요청하면 남은 승인 클래스로 5단계부터 다시 진행합니다.

## 결과 보고

- 클래스별: 증거, 선택한 수준, 상위 수준을 쓰지 못한 이유.
- 이번에 적용한 클래스: 새 검사가 과거 실수에 실패한 출력(새 검사의 메시지임을 대조한 결과 포함)과 현재 코드에서 통과한 출력.
- 5단계 1항에서 구조적 변경만 적용하고 중단했으면 그 사실과 남은 동작 변경.
- 예외로 처리한 위치 목록.
- 대응표에 추가하거나 바꾼 행.
- 줄일 수 있는 문서 조항 제안.
- 남은 승인 클래스 목록. 커밋 후 진행을 요청하면 이어서 적용한다는 안내.
- 1단계에서 건너뛴 출처가 있으면 그 사실.

## 하지 말아야 할 것

- 상위 수준(아키텍처·타입·린터·테스트)으로 막을 수 있는 실수를 문서 조항만으로 대응하지 않는다.
- 실제로 한 번만 발생한 실수를 클래스로 만들지 않는다. 금지 패턴 조항이나 대응표를 발생 횟수에 세지 않는다.
- 과거의 실제 실수에 실패함을 증명하지 않은 검사를 완료로 보고하지 않는다.
- 새 검사가 아닌 원인(컴파일 오류, 의존성 누락 등)으로 난 실패를 증명으로 기록하지 않는다(6단계).
- 사용자 확인(4단계) 없이 강제 수단을 적용하지 않는다.
- 구조적 변경과 동작 변경을 커밋 없이 이어서 적용하지 않는다(5단계 1항).
- 한 실행에서 두 클래스 이상을 적용하지 않는다. 클래스 하나를 마치면 중단하고 사용자 커밋을 기다린다(7단계 4항).
- 구조로 막힌 문서 조항을 승인 없이 삭제하지 않는다.
- 사용자 확인 없이 예외 주석을 달지 않는다(5단계 3항).
- 6단계에서 만든 worktree나 임시 재현 코드를 남긴 채 종료하지 않는다.
- 자동 커밋하지 않는다.
